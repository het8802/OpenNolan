How the OpenNolan backend works

A guided tour of the desktop app, the AI agent, and the ~100 production tools it drives — how tools are discovered, registered, and run, and which file does what.

TL;DR — the one idea that makes everything click

🔑

The agent does not register OpenNolan's tools as native LLM tools. The agent is a normal Claude Code session. Its real tools are the Claude Code built-ins — Read, Write, Edit, Bash, Glob, Grep, Skill, WebSearch, WebFetch — plus one tiny in-process tool, ask_user.

OpenNolan's ~100 production tools (motion_ops, keyframe_animate, video_compose, every TTS/image/video provider…) are plain Python classes. The agent runs them as Python through the Bash tool:

# This is literally how the agent "calls" a tool — it writes Python and runs it via Bash:
python -c "
from tools.video.motion_ops import MotionOps
r = MotionOps().execute({'operation':'pan_zoom','input_path':'clip.mp4','preset':'punch_in'})
print(r.success, r.data)
"

So there are two different meanings of "tool" in this repo, and keeping them apart is the whole game:

1. Agent tools (LLM-facing)

The handful of capabilities the language model can invoke directly. Defined by the Claude Agent SDK, gated by a permission policy in server/agent_runner.py. The only custom one is ask_user.

2. OpenNolan tools (Python)

~100 BaseTool subclasses under tools/. Each has an execute(inputs) → ToolResult. The agent reaches them only by writing Python and running it through Bash. The Tool Registry exists to describe these so the agent knows what's available — not to expose them to the model.

💡
Why this design? A tool-name allowlist is useless when every tool runs as a Bash python -c "…" string — so the safety layer inspects the command string for destructive patterns instead. It also means adding a new tool is just adding a Python file; the agent discovers it through the registry, no SDK plumbing, no restart.

Entry point #1 — the desktop app boots

You run ./run-desktop (or ./run-desktop --dev). That bash script installs node deps if missing, sanity-checks Python, warns if no Anthropic key, then launches Electron. From there:

1

Electron main process starts

desktop/main.js → app.whenReady().then(boot). In prod it grabs a free port; in dev it targets :8000 and Vite's :5173.

2

It spawns the Python backend as a child process

spawn(pythonBin(), ['-m','uvicorn','server.app:app',
      '--host','127.0.0.1','--port', PORT],
      { cwd: REPO_ROOT,                       // so `lib.*`, `server.*`, `tools.*` import
        env: { ...process.env, OPENNOLAN_PROJECTS_DIR } })

Python is resolved as OPENNOLAN_PYTHON → repo .venv/bin/python → python3.

3

It polls /api/health until the backend is alive

waitForHealth() hits GET /api/health every 300 ms (30 s budget). If the child dies first, it shows the last 20 lines of backend stderr in a dialog.

4

It opens a BrowserWindow pointed at the backend

Prod loads http://127.0.0.1:PORT — same-origin with the API, so the UI's relative /api/... calls work with no CORS. The window is sandboxed (contextIsolation, nodeIntegration:false) with a strict CSP; external links open in the system browser.

5

FastAPI serves both the API and the built UI

server/app.py mounts web/dist as static files at / — but only after every /api/* route, so the API always wins. In dev, Vite serves the SPA and proxies /api to :8000 instead.

🔌
The backend is the whole product; Electron is a thin shell. You can ignore Electron entirely and run uvicorn server.app:app + the Vite dev server to get the same app in a browser. The run-dev script does exactly that.

Entry point #2 — the agent

There are two ways the same AI agent runs against this repo. Both obey the identical contract (CLAUDE.md → AGENT_GUIDE.md), because both load the project's CLAUDE.md.

A · Headless, inside the app

When you chat in Mission Control, POST /api/projects/<id>/chat streams a turn. The AgentRunner (server/agent_runner.py) starts a Claude Agent SDK session — which itself drives the local claude CLI as a subprocess — with a system prompt that re-asserts the contract.

B · A human in a terminal

A developer runs claude in the repo root. It reads CLAUDE.md (which forces a read of AGENT_GUIDE.md / RULES.md) and behaves like the same production agent. The behavioral spikes that validated the headless runner were first proven this way.

Auth (BYOK)

The SDK reads credentials from the environment, in this order of preference:

CLAUDE_CODE_OAUTH_TOKEN
From claude setup-token — uses your Claude subscription (no per-token billing). Preferred.
ANTHROPIC_API_KEY
Per-token API billing. Takes precedence if set, so the docs tell you to unset it when using the OAuth token.
(neither)
auth_configured() also returns true if a logged-in claude CLI is resolvable — it self-authenticates from its own stored login. So a machine already logged into Claude Code needs no env var at all.

If none of these is available, the chat endpoint returns 503 with setup guidance instead of failing silently. Read/write/render all still work — only chat is gated.

How the agent discovers & calls tools

Discovery happens in two phases: first the agent learns what's possible (the capability menu), then it invokes a specific tool by writing Python.

Phase 1 — Preflight: "what can I do?"

Before any creative work, AGENT_GUIDE.md tells the agent to run a one-liner that asks the registry for a human-ready capability rollup:

python -c "
from tools.tool_registry import registry
import json
registry.discover()                              # import + register every tool
print(json.dumps(registry.provider_menu_summary(), indent=2))
"

That returns four fields the agent paraphrases for you: composition_runtimes (ffmpeg / remotion / hyperframes booleans), capabilities[] ("10 of 16 video providers configured" + provider lists), setup_offers[] (one-env-var fixes), and runtime_warnings[]. The backend runs the very same call once for GET /api/capabilities and caches it.

Phase 2 — Invocation: run the chosen tool

Having picked a tool, the agent writes Python that imports the class and calls .execute(params), then runs it through Bash. The uniform return type is ToolResult (.success, .data, .error, .artifacts, .cost_usd).

⚠️
Naming convention the agent must respect: classes are PascalCase with no "Tool" suffix — tools.video.video_compose → class VideoCompose; tools.audio.music_gen → MusicGen. And it's always .execute(dict), never .run().

When does registration happen? (your specific question)

⏱️

Not at install time. Not at "downloading dependencies". At runtime, on first use, by reflection.

There is no build step, no generated manifest, no decorator side-effect at import. Registration is a live filesystem walk of the tools/ package that runs the first time someone asks the registry a question — typically the agent's preflight, or the backend's first /api/capabilities request. It's memoized after that (ensure_discovered() only walks once).

The Tool Registry — tools/tool_registry.py

A single global registry = ToolRegistry() instance. Its job: find every tool, report availability, and group capabilities for the agent. Here's the discovery engine, the heart of "registration":

def discover(self, package_name="tools"):
    self._load_dotenv()                          # so env: deps resolve during status checks
    package = importlib.import_module(package_name)
    for module_info in pkgutil.walk_packages(package.__path__, "tools."):
        if module_info.name.endswith((".base_tool", ".tool_registry")):
            continue
        module = importlib.import_module(module_info.name)   # importing the file…
        self.register_module(module)                          # …then reflect on it

def register_module(self, module):
    for _, cls in inspect.getmembers(module, inspect.isclass):
        if cls is BaseTool or not issubclass(cls, BaseTool):  continue
        if cls.__module__ != module.__name__ or inspect.isabstract(cls): continue
        self.register(cls())                      # instantiate + index by tool.name

What that means, step by step

  • Walk — pkgutil.walk_packages recurses the tools/ tree and imports every .py file (skipping the base class and the registry itself).
  • Reflect — for each imported module, inspect.getmembers finds every class that (a) subclasses BaseTool, (b) is defined in that module (not imported into it), and (c) isn't abstract.
  • Instantiate & index — each qualifying class is constructed into an instance (tool = cls()) and stored in the registry's dict keyed by its name. That's the entire "registration."
🗂️

The dictionary is self._tools on the ToolRegistry instance — and since the module exposes a singleton, you reach it as registry._tools. It's declared self._tools: dict[str, BaseTool] = {}.

The value is a live instance, not the class. register() does self._tools[tool.name] = tool, where tool = cls(). So the key is the string tool.name and the value is a constructed object the registry can call methods on (.get_status(), .get_info(), .execute()) — impossible on a bare class.

➕
Adding a tool = adding a file. Drop a BaseTool subclass anywhere under tools/, give it a name and a capability, and it shows up in the menu and through the relevant selector automatically. No registration call, no list to edit.

Across all of these, availability is computed live by tool.get_status() → check_dependencies() — so a tool flips to "available" the moment you add its API key to .env, with no code change and no re-registration.

The BaseTool contract — tools/base_tool.py

Every tool inherits one abstract base. It enforces a uniform shape for discovery, dependency-checking, cost estimation, idempotency, and execution. The two methods that matter most:

execute(inputs) → ToolResult

The only abstract method. Takes a params dict, returns a ToolResult dataclass: success, data, artifacts (file paths produced), error, cost_usd, duration_seconds, seed, model.

check_dependencies() → status

Reads the dependencies list and verifies each. Three prefixes:
cmd:ffmpeg → must be on PATH · env:FAL_KEY → env var must be set · python:torch → module must import. Missing → tool reports UNAVAILABLE.

The metadata every tool declares (this is what the menu reads)

name
Unique key the registry indexes by, e.g. "motion_ops".
capability
The family — video_post, tts, image_generation, analysis… Selectors route on this.
provider
The backend — ffmpeg, elevenlabs, fal, selector…
runtime
LOCAL free/offline · LOCAL_GPU needs VRAM · API costs money · HYBRID either.
dependencies
The cmd:/env:/python: list that drives availability.
best_for / not_good_for
Plain-language guidance the agent reads instead of guessing.
fallback_tools
What to try if this tool is unavailable.
input_schema
JSON-schema of accepted params (also used to validate & document).
agent_skills
Names of .agents/skills/ the agent should read before using this tool.
idempotency_key_fields
Which inputs form the cache key (so repeated calls are cheap).

Note: _load_dotenv() runs at import time in this file too, so API keys are in os.environ before any tool is even instantiated.

Anatomy of a tool — two archetypes

You asked specifically about motion ops and keyframe animations. They're the perfect pair, because they represent the two fundamentally different kinds of tool in this codebase.

🎞️ Pixel-baker · motion_ops
📝 Spec-emitter · keyframe_animate

A pixel-baker reads a clip, runs FFmpeg, and writes a NEW derived clip. The output becomes a cuts[].source at the edit stage. tools/video/motion_ops.py (788 lines, capability=video_post, provider=ffmpeg, LOCAL).

One tool, eight operations dispatched in execute():

def execute(self, inputs):
    op = inputs["operation"]            # freeze | reverse | speed | segment_volume |
                                        # volume_boost | pan_zoom | clip_fx | flip
    if   op == "reverse":  err = self._reverse(src, out, has_audio)
    elif op == "speed":    err = self._speed(src, out, inputs, has_audio)
    elif op == "pan_zoom": err = self._pan_zoom(src, out, inputs, has_audio)
    # … each builds an ffmpeg command list and runs it
    probed = self._probe(out)           # re-probe! freeze/speed change duration; rotate swaps WxH
    return ToolResult(success=True, data={"output_path": str(out),
                      "duration_seconds": probed["duration_seconds"], ...},
                      artifacts=[str(out)])

Each op is just a carefully-built FFmpeg invocation. _reverse → -vf reverse -af areverse. _speed → setpts=PTS/factor + a chained atempo (atempo only spans 0.5–2.0, so it chains to cover 0.5–4.0×). pan_zoom pre-upscales ~4× before zoompan so slow zooms don't stair-step on the integer pixel grid. It can optionally register the derived clip into an asset_manifest with provenance.

🎯
Mental model: a pixel-baker is expensive and irreversible — it produces real new bytes. Other bakers: auto_reframe, silence_cutter, color_grade, object_cutout, green_screen_processor.

A spec-emitter writes a small piece of JSON into the edit plan and renders nothing. tools/video/keyframe_animate.py (316 lines, capability=video_post, provider=keyframes, LOCAL, no FFmpeg dependency).

Its whole job is to produce the keyframes list that lives inside an overlays[] item in edit_decisions.json:

def execute(self, inputs):
    overlay = inputs["overlay"]              # must have asset_id, start/end_seconds, position
    if preset:  keyframes = self._expand_preset(preset, overlay, params)  # "slide_in_left" → frames
    else:       keyframes = self._normalize_keyframes(raw)                # validate raw [{t,x,y,scale,opacity,...}]
    animated = {**overlay, "keyframes": keyframes}
    self._validate_overlay(animated)         # embed in a throwaway edit_decisions, run the REAL schema validator
    # optionally merge straight into an existing edit_decisions.json (validate-before-write)
    return ToolResult(success=True, data={"overlay": animated, "keyframes": keyframes})

A preset like slide_in_left, fade_in, pop, or ken_burns expands into keyframes relative to the overlay's own position/timing — so the agent can say "slide the logo in from the left over 0.5 s" without hand-authoring frames. The keyframes are interpreted later by the renderer (video_compose's overlay path renders position/scale/opacity; rotation is dropped on the FFmpeg path with a warning and routed to Remotion/HyperFrames).

🎯
Mental model: a spec-emitter is cheap and reversible — it just edits the plan. This is the foundation of "render-once, edit-cheap": describe the edit now, render once at the end.

The document they both revolve around: edit_decisions.json

This schema-validated file (schemas/artifacts/edit_decisions.schema.json) is the single source of truth for an edit: a list of cuts[] (source clip + in/out + speed + transform + transitions), overlays[] (text/image/cutout with position, opacity, and keyframes), an audio block (music/narration/sfx), and a locked render_runtime. Spec-emitters write into it; the renderer reads it; the manual editor and the agent both edit it through the same schema gate.

Selectors & scoring — picking a provider

For capabilities with many interchangeable providers (TTS, image, video, web-image-search, screen-capture), a selector tool sits in front. Selectors auto-discover providers and rank them, so adding a provider needs zero selector changes.

Discovery — from the registry

# tools/audio/tts_selector.py
def _providers(self):
    from tools.tool_registry import registry
    registry.ensure_discovered()
    return [t for t in registry.get_by_capability("tts")
            if t.name != self.name]

Drop in tools/audio/whatever_tts.py with capability="tts" and it appears here instantly.

Routing — score, then delegate

def execute(self, inputs):
    candidates = self._providers()
    tool, score = self._select_best_tool(inputs, candidates, ctx)
    result = tool.execute(inputs)         # delegate to the winner
    result.data["selected_provider"] = tool.provider
    result.data["selection_reason"]  = score.explain()
    return result

Order: explicit preferred_provider → highest score among available providers. An operation:"rank" mode returns the scoreboard without generating.

The scoring engine — lib/scoring.py

rank_providers(tools, task_context) returns a sorted list of ProviderScore objects. The weighted formula: 30% task-fit · 20% quality · 15% control · 15% reliability · 10% cost · 5% latency · 5% continuity. It pulls each tool's quality_score / historical_success_rate when set, else falls back to stability-based heuristics. Every score carries an .explain() so the agent can tell you why it picked a provider.

The three selectors: tts_selector, image_selector, video_selector (plus web_image_search and screen_capture_selector). All provider="selector", and the registry deliberately excludes selectors from the provider menu so they don't double-count.

The render engine — tools/video/video_compose.py

The biggest tool in the repo (~4,100 lines). It's the one that turns an edit_decisions.json into a finished video. execute() is an operation switch:

def execute(self, inputs):
    op = inputs["operation"]
    if   op == "compose":        return self._compose(inputs)
    elif op == "render":         return self._render(inputs)            # full timeline → final mp4
    elif op == "render_proxies": return self._render_proxies(inputs)    # render-once: per-scene cache
    elif op == "remotion_render":return self._remotion_render(inputs)
    elif op == "burn_subtitles": return self._burn_subtitles(inputs)
    elif op == "overlay":        return self._overlay(inputs)          # keyframed overlays
    elif op == "encode":         return self._encode(inputs)

Three render engines, one tool

The render_runtime field (locked at the proposal stage, carried unchanged through edit_decisions) decides which engine runs. Silent swaps are forbidden — if the locked runtime is unavailable, the agent must escalate, not quietly fall back.

FFmpeg

Footage-led edits: cuts, concat, trim, xfade transitions, keyframed/text overlays, PiP, crop, custom canvas, subtitle burn. Always available (just needs the ffmpeg binary). Video sources only — a still image in cuts[] is rejected and routed to Remotion.

Remotion

React-based: still images → animated scenes, text/stat cards, charts, callouts, spring transitions, word-level captions, TalkingHead. Needs Node + remotion-composer/ + node_modules.

HyperFrames

HTML/CSS/GSAP: kinetic typography, product promos, launch reels, website-to-video, SVG rigs. Needs Node ≥ 22 + FFmpeg + npx hyperframes.

Routing is automatic (_render_via_ffmpeg / _remotion_render / _render_via_hyperframes), but the agent is required to know all three exist at proposal time so it designs the visual treatment intentionally. There's also a HARD RULE never to silently tonemap HDR footage to SDR — detected via is_hdr_source() in tools/video/_shared.py.

"Render-once, edit-cheap" — the NLE model

Rendering a scene is expensive; rearranging an edit (order, transitions, audio, trims) is cheap. So OpenNolan renders each scene once, caches it by its content identity, and reuses it across edits. Only a scene whose pixels actually change misses the cache.

The content-addressed cache — tools/video/render_cache.py

class ProxyCache:                       # ~/.cache/opennolan/proxies/<sha256>.json
    @staticmethod
    def key(identity):                  # sha256 over a canonical identity dict
        return sha256(json.dumps(identity, sort_keys=True))
    def get(self, key):                 # HIT only if the record AND its clip file still exist
    def put(self, key, record):         # atomic temp→os.replace; cross-process flock
🧬
The identity must fold in the content hash of each source file (file_content_hash()), not just its path/id. A regenerated upstream asset keeps its id but changes pixels — keying on the id alone would serve a stale proxy. Descriptive fields (labels, "reason") are excluded so cosmetic edits don't cause false cache misses.

How an edit re-renders

1

You edit the timeline & hit Render

The Studio UI PUTs the new edit_decisions.json (schema-gated), then POST /api/projects/<id>/render.

2

A background job runs render_proxies

server/render_jobs.py → RenderJobStore resolves project-relative paths to absolute, then calls video_compose.execute({operation:"render_proxies", …}) on a daemon thread. The UI polls GET …/render/<job_id>.

3

Each scene is hashed → cache hit or re-render

Unchanged scene → reuse its cached proxy clip. Changed scene → re-render just that one. This is why a small tweak to scene 3 doesn't re-render scenes 1, 2, 4, 5.

4

Cheap FFmpeg concat → final mp4

The proxies are concatenated (cheap) into projects/<id>/renders/editor_preview_<job>.mp4. The manual editor reuses the exact same video_compose path the agent's compose stage uses, so preview == export.

Pipelines, checkpoints & stage status — lib/

Above the tools sits a thin orchestration layer. The agent follows a pipeline (an ordered list of stages); it records progress as checkpoints; the UI stepper reads those checkpoints live.

Pipelines — lib/pipeline_loader.py + pipeline_defs/*.yaml

Each YAML manifest (e.g. talking-head.yaml, instagram-reels-studio.yaml) declares ordered stages, each with: a director skill to read, required_tools / optional_tools, expected artifacts, a checkpoint policy, and human-approval gates. load_pipeline() / get_stage_order() parse them; list_pipelines() backs GET /api/pipelines.

Projects — lib/project.py

create_project() scaffolds projects/<id>/ with assets/ subdirs (images/video/audio/music) and a project.json manifest that carries the chosen pipeline_type. list_projects(), get_project_record(), sanitize_filename() guard the API's write paths.

Checkpoints — lib/checkpoint.py

The source of truth for progress. write_checkpoint() atomically records a stage's status (+ validates its artifacts against schemas). get_completed_stages() / get_next_stage() let a fresh or resumed agent pick up exactly where the last one stopped.

The stepper bridge — scripts/update_stage.py

The one-liner the agent shells out to so the UI updates in real time:
python scripts/update_stage.py <id> <stage> in_progress|completed|awaiting_human <pipeline>. It just calls write_checkpoint(). The backend's FileStateSource (server/state.py) reads those files for GET …/state.

Agent runner internals — server/agent_runner.py

This is the safety + lifecycle layer around the Claude Agent SDK. Four things worth understanding:

1 · The permission gate (decide_tool → can_use_tool)

Since tools run as Bash strings, a tool-name allowlist can't capture the risk. So:

  • Safe tools (Read, Glob, Grep, WebSearch…) and write tools (Write, Edit) → allowed automatically.
  • Bash → the command string is regex-scanned for ~14 destructive/exfil patterns (rm -rf, sudo, git push, curl … | sh, fork bombs, raw dd, network uploads…). A match → a UI confirm_request; clean → allowed.
  • Unknown/MCP tools → conservatively routed to confirm.

With no confirm handler (fully unattended), flagged calls are denied — the safe default. A hard max_budget_usd ceiling (default $15) is enforced SDK-natively.

2 · ask_user — the one custom tool

Registered as an in-process MCP server (create_sdk_mcp_server("mc", …)). When the agent calls it, the runner emits a question SSE event and blocks on a future until POST …/agent/answer resolves it. The built-in AskUserQuestion is disallowed so the agent uses this controllable round-trip instead.

3 · Per-project sessions & resume

One persistent SDK client per project (lazy, reused) so conversation context survives across turns and the awaiting-human → approve → resume flow works. If a session dies (budget ceiling, transport crash), the next turn rebuilds with the prior session_id so the agent comes back with its full context on a fresh budget. A first-turn preamble also grounds it in on-disk checkpoints/artifacts — so even after a cold backend restart it resumes instead of redoing work.

4 · The system prompt

Re-asserts the contract every headless run: read CLAUDE.md → AGENT_GUIDE.md, read the per-stage skill, checkpoints live under projects/, present both Remotion and HyperFrames runtimes, announce cost before paid generation, stop at approval gates. setting_sources=["project"] is what makes the SDK load CLAUDE.md in the first place.

A Vite + React SPA. Two halves: Mission Control (chat + pipeline + assets) and the from-scratch Studio NLE.

The API client — api.js

Thin fetch wrappers for every endpoint, plus chatStream() — an async generator that parses the SSE stream into assistant / result / confirm_request / question / error events for App.jsx to render.

The pure core — editor/interp.js

End-to-end: "make me a 30-second reel"

Putting it all together — one request, traced through every layer.

1

UI → backend

You create a project and type a brief. App.jsx opens an SSE stream to POST …/chat; AgentRunner starts/continues the project's SDK session with a project-binding preamble.

2

Agent preflight

The agent reads CLAUDE.md → AGENT_GUIDE.md, then runs (via Bash) registry.discover(); registry.provider_menu_summary() to learn what's configured, and presents the "N of M" capability menu.

3

Plan & pick a pipeline

It reads a pipeline_defs/*.yaml, proposes concepts, and (via ask_user) asks you to choose. It locks a render_runtime. It marks stages with scripts/update_stage.py → the UI stepper moves.

4

Generate & process (Python tools via Bash)

It calls provider tools through selectors — tts_selector.execute(...), video_selector.execute(...), music_gen, motion_ops for camera moves, keyframe_animate for overlay motion. Each is a Bash python -c running .execute(). Paid calls announce cost; destructive Bash pauses for your confirm.

5

Assemble the edit

All choices land in edit_decisions.json (schema-validated). video_compose renders it — each scene cached by content hash, then concatenated. Output to renders/; a checkpoint marks the stage complete; the Activity log records every tool touched.

6

You take over in the Studio editor

Open the timeline, trim/reorder/keyframe by hand. Each Save re-validates through the same schema; each Render reuses cached scenes (render-once) so iterating is fast. Preview == export, because the editor calls the very same video_compose path.

🎬
That's the whole system: a Claude Code agent that drives ~100 Python tools via Bash, records its work as checkpoints + a schema-gated edit plan, renders once and caches, and hands you a real NLE to finish by hand — all inside a local Electron + FastAPI app you bring your own keys to.
