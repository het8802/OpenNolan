A native-feeling Mac app for OpenNolan — without a rewrite

Wrap the local Mission Control stack you already have in an Electron desktop app, and add a “render once, edit cheaply” editing model so edits stop triggering full re-renders.

📅 Drafted 17 Jun 2026 👤 Owner: Het 🎯 Goal: validate if it's worth building 🔑 BYOK, local render, no cloud

The one-paragraph version

The hard engine already exists and runs on your machine — local rendering, a timeline file format, and an FFmpeg “assemble the clips” step. This app adds two things: (1) an Electron window so it's a real Mac app, and (2) a brand-new editing UI, built from scratch, that feels like real editing software — the current web editor isn't good enough to keep. Underneath: the AI renders each piece of a video once into clips, drops them on a timeline, and from then on every edit (trim, 2×, crop, transitions, keyframes) is instant through FFmpeg — no re-rendering the animations each time. Think “export your clips, then edit them in a real editor,” not “re-export the whole project on every tiny change.”

✏️ Edit mode: click it, then type directly into any text to revise it. 💬 Comment: hit “+ comment” on any section to leave a note. ⬇️ Export: download your edits + comments as a file to hand back to me. 💾 Everything saves automatically in this browser.

How the app is wired

+ comment▼

The Electron app is a thin shell. On launch it starts your existing Python server in the background, then opens a window showing your existing React UI. Nothing about your editor or pipeline gets rewritten — they get wrapped.

💡 In plain terms: the app is a frame around your existing software. The frame's only jobs are “turn the engine on when you open it” and “show your screen.” That's why it's days of work, not months.
3

The editing model — “render once, edit cheaply” 🆕 the real value

+ comment▼

This is the part that fixes your complaint about the web app, where every edit forces a full re-render. We split production into two phases:

Phase A — build the pieces (heavy, happens once)

When you prompt for a video, the agent renders each composition (a Remotion scene, a HyperFrames animation, or an AI-generated clip) into its own clip file, saved in assets/video/. Each clip is tagged with a fingerprint of its content so it's only ever rendered once.

Phase B — assemble & edit (cheap, happens constantly)

All those clips get placed on the timeline (edit_decisions.json) as a sequence of cuts. The final video is assembled with FFmpeg. From here on, every edit you or the agent make — trim, 2× speed, crop, transition, overlay — only re-runs FFmpeg, which is fast. The expensive animations are never re-rendered.

⚖️ The one rule that makes it work: FFmpeg edits the arrangement of clips. If you want to change what's inside a composition (different text, different animation), that one clip gets re-rendered — but only that one, and only when its content actually changes.

Same tools for you and the agent

The agent and the manual editor both read and write the exact same timeline file. So whatever the AI can do (speed, cut, crop, keyframe-animate, overlay), you can do by hand on the same timeline — and vice versa.

4

What we keep vs. what we rebuild

+ comment▼

The engine already shipped on main — but the editor UI doesn't meet the bar. So the rule is: keep the engine, rebuild the front-end.

Keep — the engine (reuse as-is)

  • ✅ Timeline file format — edit_decisions.json already supports cuts (source, in/out, speed, crop, layer/picture-in-picture), overlays, transitions, keyframes, subtitles. This is the shared contract.
  • ✅ Server endpoints — read/write the timeline + start a background render (replaces any in-progress one), with safe atomic saves
  • ✅ FFmpeg assembler — joins all clips on a timeline; preview = export (what you see is what renders)
  • ✅ Shared with the agent — the agent reads/writes that same timeline file, so a new UI stays in sync with it automatically

Rebuild — the editor UI (from scratch)

  • 🆕 The current web editor (web/src/editor/) is not reused — its UX isn't good enough. Reference only.
  • 🆕 A new editing-software-grade UI is built fresh for the app (see WS3). It talks to the same edit_decisions.json + render endpoint, so we rebuild only the surface, not the engine.
💡 Key point: rebuilding the UI is not rebuilding the editor. The data model, save logic, render path, and agent-sharing all stay. The new UI is just a far better front-end on the same proven engine.

The build, in four workstreams

+ comment▼

WS1 · Electron shell

the containereffort: small–medium
  • New desktop/ folder: Electron main process + build config
  • On launch: start Python server, wait for it to be healthy, then open the window; shut it down on quit
  • Dev mode points at the live Vite server; packaged mode loads the built UI
  • First-run key screen: paste your Anthropic + provider keys → saved locally
  • Switch the agent's login from claude setup-token to a plain ANTHROPIC_API_KEY (so a normal download works)

WS2 · Compositions → timeline clips

the real engineeringeffort: medium
  • Change the compose step to render each composition to its own clip (not one final video)
  • Add a content fingerprint + cache so a clip is rendered once and reused
  • Auto-write a timeline whose cuts point at those clips, set to the FFmpeg assembler
  • “Re-render only what changed” logic

WS3 · Editing-software UI — built from scratch

the other big buildeffort: medium–large

The current web editor isn't good enough, so we build a new one that feels like real editing software (CapCut / Premiere / iMovie). It reads & writes the same timeline file, so you and the agent stay in sync.

  • Timeline: multi-track, drag to reorder, trim handles, playhead/scrubber, zoom, snapping, split
  • Click a clip → its tools appear as buttons — only the ones valid for that clip: Speed (2×/4×…), Crop, Transform (scale/position), Opacity, Transitions (in/out), Volume, Text / overlay, Motion (pan/zoom)
  • Keyframe any animatable property with easing — a real keyframe lane
  • Regenerate clip: re-prompt a single composition (re-renders just that one clip)
  • Preview that matches the export, plus undo / redo
  • Every button maps to a tool the engine actually renders — no dead controls (e.g. rotation isn't rendered, so it won't be a button)
🎯 MVP cut: nail timeline + click-clip tools + Speed / Crop / Trim / Split / Transitions + keyframes + preview first. Defer the long tail (every transition type, advanced snapping/ripple) so it feels like an NLE without becoming a 3-month build.

WS4 · Bundle the runtimes

the packaging hurdleeffort: medium
  • Python: package the server so it runs without a dev setup (the main time-sink)
  • FFmpeg: ship the binary, point the tools at it
  • Node (Remotion/HyperFrames): see the open decision in §7 — bundle vs. install on first use

Risks & what comes after the MVP

+ comment▼

Things that could bite

  • Packaging Python — bundling a Python app with all its dependencies is the classic “harder than it looks” step. It's the main reason WS4 is medium, not small.
  • Cache correctness — the “only re-render what changed” logic has to be right, or you'll either re-render too much (slow) or too little (stale clips).
  • Port already in use — if something else uses port 8000, the app should pick a free port automatically.

The “if this wins” path (deferred on purpose)

If the MVP proves people want this, the upgrades are: code-signing + notarization (so others can install it), auto-update, Windows/Linux, and eventually — if you want flagship-grade timeline performance — a native Swift version (like ChatGPT's Mac app). That's a reward for a proven idea, not a starting bet. Electron lets you find out first, cheaply.
